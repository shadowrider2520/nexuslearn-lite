01What the app does

One account, invite-only study rooms, and three AI-powered study tools layered on top of a shared roadmap.

🏠

Study rooms

Anyone with an account creates a room, gets a 6-character invite code (e.g. K7QX2M), and friends join with that code. Rooms are named, renamable, and list every member with their progress.

rooms · room_members
🗺️

AI roadmaps + tasks

Paste a topic, pick minutes-per-day and detail level, and Groq generates a day-wise plan. Each step can spawn 2–4 hands-on tasks or mini-projects. Everyone checks items off independently — progress is per member.

roadmaps · progress · tasks · task_progress
🧑‍🏫

AI tutor chat

A live room chat where the AI tutor answers with the roadmap and the last 15 messages as context. It's coached to teach Socratically, notice effort, switch languages on request (even Tanglish), and take breaks when the room has been grinding.

messages

02System architecture

Four actors. The browser talks to Supabase directly (auth, reads, realtime) and to the Next.js server for anything involving the Groq API or writes. The numbered callouts map to the flows in section 04.

How to read it: ① the room page holds all state · ② form actions and API fetches go to the server · ③ server-side Supabase client uses the user's cookies · ④ the three API routes call Groq · ⑤ the browser talks to Supabase straight through the anon key — security relies on RLS policies, not the app.

Relationship map
Shape of the data: roadmaps.steps is one JSON blob of {day, id, title, description, estimated_minutes} with globally-flattened IDs (step 7 might be Day 3). tasks.items is a JSON array of {id, type: "task"|"project", title, description}. Progress is stored per user with composite upserts — that's how the "Completed by: …" list works.

04Core flows

Five journeys through the system. Actors: CLIENT SERVER SUPABASE GROQ

CLIENT
Sign up or log in with email + password
supabase.auth.signUp({ email, password }) / signInWithPassword(...)
Handled by the browser client, straight to Supabase Auth.
SUPABASE
Auth issues a JWT session; browser stores sb-* cookies
The anon key in the client can only do what the JWT + RLS allow.
CLIENT
Router sends new users to /set-username, which inserts a profiles row keyed by user.id
profiles.insert({ id: user.id, username })
CLIENT
Every protected page first checks auth.getUser(), then checks a profile exists — missing profile → /set-username, no user → /login
SERVER
proxy.ts refreshes the session on every matching request (matcher excludes static assets)
createServerClient(...) → supabase.auth.getUser() → rewrites cookies
Next 16's renamed middleware; keeps long-lived sessions alive.
Takeaway: auth is entirely delegated to Supabase — the app's only job is deciding which screen comes next based on whether a profile row exists.
CLIENT
Home page form submits to the createRoom or joinRoom server action
<form action={createRoom}> … <input name="name">
SERVER
Action re-verifies the user server-side, generates a 6-char uppercase invite code
const inviteCode = nanoid(6).toUpperCase()
createRoom also runs rpc("whoami") and logs it — a debug leftover.
SERVER
Inserts rooms (created_by = user.id), then inserts a room_members row for the creator
SERVER
Join: looks up rooms by invite_code and inserts a membership; errors surface as thrown messages
CLIENT
redirect(`/room/${room.id}`) lands everyone in the room; the room page loads members and subscribes to realtime
CLIENT
Exit = leaveRoom action: deletes the membership row, redirects home
Takeaway: rooms are just a rooms row plus a membership join table. Membership changes are broadcast to everyone via the members-{roomId} channel.
CLIENT
Two-step form: topic → prefs (minutes/day, detail: quick | detailed | thorough)
POST /api/roadmap { topic, roomId, minutesPerDay, detailLevel }
SERVER
Route builds a strict-JSON system prompt — "Respond ONLY with valid JSON"
{ "topic": string, "days": [ { "day": 1, "items": [{ "id", "title", "description", "estimated_minutes" }] } ] }
GROQ
llama-3.3-70b-versatile at temperature 0.4 returns the day-wise plan
SERVER
Parses the JSON (invalid → 500), then flattens days into one list of steps with global sequential IDs
steps = days.flatMap(d => d.items.map(item => ({ id: globalId++, day: d.day, ... })))
SERVER
Inserts into roadmaps (room_id, topic, steps) and returns the new id
CLIENT
Sets it as the active roadmap; progress/task channels for that roadmap come online
Takeaway: the roadmap is generated once, stored as a blob, and every member sees the same days. Only the creator's settings (minutes/day, complexity) shape it — there's no per-member personalization.
CLIENT
Per step, "Generate tasks & mini-project"
POST /api/tasks { roomId, roadmapId, stepId, stepTitle, stepDescription }
GROQ
Returns 2–4 concrete hands-on items, each typed "task" or "project" — prompt forbids "more theory"
SERVER
Upserts into tasks keyed on (roadmap_id, step_id)
tasks.upsert({...}, { onConflict: "roadmap_id,step_id" })
Regenerate simply replaces the same row — one task set per step, ever.
CLIENT
Renders tasks with their own checkboxes; task_progress tracks each member's completion per task
Takeaway: tasks are a second JSON blob layered onto a step. Projects render purple, tasks blue — a nice touch: the AI decides which is which, and the UI just styles it.
CLIENT
User types → sendMessage() → POST /api/chat
POST /api/chat { roomId, content }
SERVER
Verifies session (401 otherwise), resolves the username from profiles
SERVER
Persists the user's message immediately (is_ai: false) — realtime shows it to the whole room while Groq still works
SERVER
Gathers context: latest roadmap (topic + steps) and the 15 most recent messages
SERVER
buildTutorPrompt() assembles the ~60-line system prompt (see §05)
GROQ
llama-3.3-70b-versatile, temperature 0.6, replies as the tutor
SERVER
Persists the reply (is_ai: true, username "AI Tutor"); returns it
CLIENT
Sender reloads messages; every other member gets the same rows pushed via the messages-{roomId} INSERT channel
Takeaway: chat is a write-then-generate pipeline. If Groq fails, the user's message is still saved and a canned "I couldn't respond right now" is stored as the AI reply — the transcript always stays consistent.

05The AI tutor's personality, in code

Most of the "product" lives inside one string. buildTutorPrompt() in app/api/chat/route.ts bakes the entire tutoring philosophy into the system prompt, then appends live context. The red section is the most defensive rule in the file.

buildTutorPrompt(topic, steps, recentMessages) → system prompt · ~1,300 words · injected into messages[0]
PersonalityWarm, patient, calls learners "buddies", never sarcastic, never irritated by repeated mistakes.
TeachingDefault: hint → attempt → praise → targeted fix → retry loop. But never withhold an explanation when asked for one, and stop the Socratic loop if the learner is stuck.
Hard ruleNEVER ANSWER A DIRECT QUESTION WITH ONLY ANOTHER QUESTION. Direct questions like "what is AI?" get answered, not bounced back.
GroupHelp the asker directly; only pull in the group for discussions, quizzes, debates — don't spam "can anyone explain?"
LanguageFollow language/style requests — including Tanglish, and keep using it until asked to switch back.
MoodDetect frustration, boredom, excitement; adapt tone, simplify, add mini-quizzes or "try this" challenges when things get stale.
BreaksAfter long study stretches, gently remind the room to stretch / drink water — briefly, not constantly.
RoadmapUse the roadmap as context, not a script — don't force Day numbers into unrelated answers; explain the roadmap only when asked.
Live dataInterpolates: current topic, the full roadmap JSON, and the last 15 messages as username: content lines.
Bottom line"You are a learning companion, not an answer machine. Help the buddies think."
Why it matters: the same route handler is used for every room, so the prompt is the only thing that makes the tutor feel room-aware. No per-room memory — the "memory" is just the last 15 messages re-sent every time.

06Realtime: how the room stays in sync

Four Supabase channels, each scoped with a row filter. When any member toggles a checkbox or sends a chat, Postgres broadcasts the change and every open tab re-fetches that slice of data.

members-{roomId}

Listens on room_members for any event → reloads the member list + progress bars.

join / leave → roster updates live

messages-{roomId}

Listens on messages for INSERT only → reloads the transcript. Fires twice per exchange (user msg, AI reply).

chat stays live for everyone

progress-{roadmapId}

Listens on progress for any event → reloads steps + per-member completion.

checkbox → everyone's % moves

task-progress-{roadmapId}

Listens on task_progress for any event → same reload path.

task checkboxes sync too
Design note: channels push events, not data — every handler just calls the same loader functions (e.g. loadActiveRoadmapData). Simple and race-proof, at the cost of re-fetching more than strictly needed. Channels are removed on unmount, so switching roadmaps doesn't leak subscriptions.

07Worth knowing

What a next contributor should know before touching this codebase — mostly informed judgment, marked where it's a guess.

Watch
The room page is one 2,100-line client component
All roadmap, task, chat, member, and form state lives in a single useState pile inside app/room/[id]/page.tsx. Every realtime event re-runs the loaders; every render re-derives dayNumbers, per-step completion, and per-member percentages. It works, but it's the ceiling for adding features.
Risk
Client-side database access is gated by RLS you can't see
The browser uses the anon key to read and upsert directly. There are no SQL files in this repo, so the security model (which user can see which room, who can write progress) lives entirely in Supabase dashboard policies. Any policy gap is reachable from the browser. Worth auditing before launch.
Info
Heavy debug logging left in production paths
app/api/chat/route.ts logs a wall of requestId-tagged lines around every step (auth, profile, inserts, Groq status, reply length), and createRoom logs rpc("whoami") vs the JWT user id — a leftover from debugging a mismatch between auth.uid() and user.id. Great for debugging, noisy in production.
Watch
Server actions don't re-verify membership
updateRoomName, deleteRoadmap, and deleteTasks skip auth and room checks entirely — any logged-in user could call them with arbitrary ids. The UI hides them from non-hosts, but the actions themselves are unguarded (again, RLS may or may not cover it).
Info
Invite codes: no collision retry
nanoid(6).toUpperCase() = ~2.2 billion combinations (36⁶) with no uniqueness constraint or retry loop — practically fine, theoretically a "Room not found" surprise if two rooms ever share a code.
Watch
Failures are silent for the user
Almost every failure path ends in console.error. A failed roadmap or task generation leaves the user staring at an unchanged screen — no toast, no inline error. Server-action errors (e.g. "Room not found") surface as raw thrown messages.
Info
Roadmap/tasks are JSON blobs, not relational rows
Steps and task items are stored as jsonb columns; "step 7" only means anything inside one roadmap's blob. Queries like "which users finished all projects" would need jsonb_to_recordset gymnastics. Fine for display, limiting for analytics.
Info
What's clean
Upsert keys are thoughtfully composite (roadmap_id,step_id,user_id etc.), realtime channels are scoped and cleaned up, Next 16 conventions are followed (proxy.ts, async params), and the AI-tutor prompt is genuinely well-designed. The bones are good.
